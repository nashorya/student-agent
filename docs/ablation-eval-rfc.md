# RFC: Component Ablation Eval for Student-Agent v0.4

Status: Draft
Owner: student-agent
Target version: v0.3D / v0.4 verification
Related guide: `docs/eval-writing-guide.md`

## 0. Purpose

This RFC defines the design for a component ablation eval before writing concrete
cases or runner code.

The goal is not to prove that every new harness component is independently good.
The goal is to make component contribution, interaction loss, and regression
risk visible through comparable runs and trace-bound metrics.

This RFC intentionally stops before implementation. Cases and runner code should
be written only after the four design questions below are accepted.

## 1. Literature Alignment

### AHE: Component Effects Are Not Additive

The roadmap records the AHE finding that component ablation can reveal
non-additive interactions:

- system prompt alone may regress
- memory, tool, and middleware each improve in isolation
- summed single-component gains can exceed the actual combined gain

Design consequence:

- The eval must compare baseline, single-component variants, and all-components.
- The eval must not assume that stacking all components equals the sum of their
  individual gains.
- If all-components underperforms the best single component, the result is not
  automatically "eval failure"; it is a regression/interaction finding that must
  be recorded.

### Meta-Harness: Scores Alone Are Not Enough

The guide and roadmap treat full traces as more useful than scores-only or
summary-only results.

Design consequence:

- The runner must write per-trial events and outcomes into Run Archive.
- Metrics must be trace-bound where the construct is about harness behavior.
- Agent-writable reports are optional diagnostics, never trusted provenance.

### AEvo: Evaluator Isolation

AEvo motivates keeping the evaluator isolated from the evolving agent to reduce
reward hacking risk.

Design consequence:

- The ablation runner must be separate from the agent under test.
- Agent runs cannot write `outcome.json`, final scores, or formal pass/fail.
- Case drafts can be generated by the agent, but frozen tasks and graders require
  human/CommitGate approval.

## 2. The Four Design Questions

### Q1. What Does The Ablation Eval Measure?

It measures the marginal and interaction effects of v0.4 harness components on
coding-agent reliability.

Primary construct:

> Stable harness contribution: whether a component reduces known failure modes
> without introducing new regressions, measured through task outcomes and
> protected trace events.

Components in scope:

- `ToolGuard`
- `ContextBuilder`
- `Signal Pipeline`
- `Hashline`

Out of scope for v0.3D:

- Semble code search
- full anti-lost recovery mode
- outcome-credited knacks
- meta-editing / self-evolution
- model-aware dynamic context budgets

The eval should cover at least these task families:

- edit correctness: precise edit, stale edit, multi-file patch
- tool safety: empty bash, broad glob, bad retry pattern
- context reliability: preference-aware edit, search-before-read, multi-phase task
- recovery observability: tool error, hashline rejection, lostness signal

### Q2. What Effects Do We Expect?

Expected measurable effects:

- Each component should create a measurable difference against baseline on at
  least one metric tied to its construct.
- All-components should be at least as good as the best single component on the
  primary success metric, or produce a recorded interaction regression.
- The sum of single-component gains is not expected to equal all-components gain.
- Components may improve one metric while worsening another; this must be
  preserved rather than collapsed into one score.

Expected per-component contributions:

- ToolGuard should reduce unsafe or pointless tool calls, especially empty bash,
  natural-language bash, broad glob, and blind retry.
- ContextBuilder should reduce context drift and improve task continuity, while
  keeping estimated prompt size bounded.
- Signal Pipeline should increase trace visibility for tool failures, guard
  blocks, hashline events, user corrections, and lostness.
- Hashline should reduce stale/incorrect edits and expose stale rejection or
  recovery events.

Regression risks to track:

- ToolGuard may over-block valid tool calls.
- ContextBuilder may omit useful context under budget.
- Signal Pipeline may add noisy signals that bias recall.
- Hashline may reject valid edits when tags are stale but recoverable.
- All-components may interact badly, e.g. ToolGuard blocks a recovery path that
  Hashline would have handled.

### Q3. What Is The Methodology?

Run the same benchmark task set under six configurations:

1. `baseline`: all v0.4 harness components disabled
2. `toolguard_only`
3. `contextbuilder_only`
4. `signal_pipeline_only`
5. `hashline_only`
6. `all_components`

Minimum task set:

- 5 tasks for the first executable version
- recommended 8-12 tasks before freezing
- each task must have stable setup, cleanup, and protected verifier output

Trial policy:

- deterministic/component checks: 1 trial is acceptable
- agentic tasks: minimum 3 trials during draft, 5 before freeze
- runner must record model, prompt, tool config, timeout, budget, and component
  flags for every trial

Data flow:

```text
case spec
  -> runner expands component matrix
  -> each trial creates runId
  -> RunArchiveWriter.startRun()
  -> agent/harness execution
  -> runner appends protected events
  -> runner computes metrics from traces + verifier
  -> RunArchiveWriter.finalizeRun()
  -> ablation report compares configs
```

The runner must not trust:

- agent-writable success files
- fixed PASS strings
- agent-authored metric summaries
- outcome files written by the agent

The runner may trust:

- protected `events.jsonl`
- protected `outcome.json`
- verifier output
- task test results produced outside the agent-visible environment

### Q4. How Many Cases And What Runner Should Exist?

RFC answer:

- Use 6 meta-cases, one per configuration group.
- Use one runner that expands the group into real task trials.
- Do not write 6 separate task bundles that duplicate environment setup.

Planned cases:

```text
ablation-baseline-001
ablation-toolguard-001
ablation-contextbuilder-001
ablation-signal-001
ablation-hashline-001
ablation-all-001
```

Each case should reference the same benchmark manifest:

```text
evals/ablation/benchmark-manifest.json
```

The manifest should contain:

- task ids
- task family
- required verifier
- required trace metrics
- expected relevant component
- regression risks

The runner should produce:

```text
evals/results/ablation/{timestamp}/
  config.json
  per-run.jsonl
  metrics-by-config.json
  comparison.md
```

It should also write normal run archives:

```text
memory/runs/{runId}/events.jsonl
memory/runs/{runId}/outcome.json
```

## 3. Metrics

Primary metrics:

- `task_success_rate`
- `verified_pass_rate`
- `tool_error_count`
- `unsafe_tool_block_count`
- `hashline_rejection_count`
- `hashline_recovery_count`
- `lostness_trigger_count`
- `user_correction_count`

Secondary metrics:

- `estimated_prompt_tokens`
- `output_tokens`
- `repeated_tool_call_count`
- `run_duration_ms`
- `trace_event_count`

Derived comparison metrics:

- `delta_vs_baseline`
- `delta_vs_best_single_component`
- `interaction_loss`

Interaction loss:

```text
single_sum_gain = sum(max(0, metric_gain(component_i)))
all_gain = metric_gain(all_components)
interaction_loss = single_sum_gain - all_gain
```

This is diagnostic, not a hard pass/fail by itself.

## 4. Pass / Investigate / Fail Rules

Pass:

- all-components task success rate >= best single-component success rate
- no P0 safety regression appears in all-components
- every component produces at least one trace-bound metric in its expected area
- all runs have `events.jsonl` and `outcome.json`

Investigate:

- all-components improves success but worsens safety/trace metrics
- single-component gains are positive but combined gain is lower than expected
- component has no measurable effect on any case
- metric source is summary-only rather than trace-bound

Fail:

- runner cannot reproduce the same task set across configs
- agent can write or spoof official outcome
- all-components regresses below baseline on primary success rate
- required trace metrics cannot be collected
- verifier is visible to the tested agent

## 5. Required Harness Support Before Cases

Do not write executable ablation cases until these exist:

- RunArchiveWriter can create `events.jsonl` and `outcome.json`
- `AblationConfig` can enable/disable ToolGuard, ContextBuilder, Signal Pipeline,
  and Hashline independently through dependency injection
- runner can create isolated run directories per config/trial
- verifier/test output is outside the agent-visible environment
- metric extraction can read protected trace events

If component flags do not exist yet, the first runner version should be a dry-run
design validator, not a real ablation runner.

### 5.1 AblationConfig

The first implementation should introduce a small config type:

```ts
interface AblationConfig {
  toolGuard: boolean;
  contextBuilder: boolean;
  signalPipeline: boolean;
  hashline: boolean;
}
```

The runner should not use process-wide environment variables or CLI flags as the
primary mechanism for component toggles. It should construct harness instances
with dependency injection:

- enabled component: inject the real hook/manager/provider
- disabled component: inject `null`, a no-op implementation, or omit the hook
  registration

This matches the existing pattern used by components such as `ReflectAgent`,
where optional managers can be passed through the constructor. It also keeps
each ablation run isolated and makes config visible in the runner output.

## 6. Proposed Case Authoring Prompt

After this RFC is accepted, ask the code generator to create:

1. `evals/ablation/benchmark-manifest.json`
2. `evals/drafts/ablation-*/spec.json`
3. `scripts/eval-ablation-runner.ts`
4. metric extraction utilities
5. tests for manifest parsing and metric comparison

The generator must not modify frozen `evals/tasks/` or formal graders.

## 7. Decisions

### 7.1 Component Flag Mechanism

Decision: use dependency injection.

Do not use environment variables or CLI flags for the first implementation.
The runner will create each harness instance from an `AblationConfig` object and
inject only the enabled components.

The six canonical configs are:

```ts
const ABLATION_CONFIGS: Record<string, AblationConfig> = {
  baseline: {
    toolGuard: false,
    contextBuilder: false,
    signalPipeline: false,
    hashline: false,
  },
  toolguard_only: {
    toolGuard: true,
    contextBuilder: false,
    signalPipeline: false,
    hashline: false,
  },
  contextbuilder_only: {
    toolGuard: false,
    contextBuilder: true,
    signalPipeline: false,
    hashline: false,
  },
  signal_pipeline_only: {
    toolGuard: false,
    contextBuilder: false,
    signalPipeline: true,
    hashline: false,
  },
  hashline_only: {
    toolGuard: false,
    contextBuilder: false,
    signalPipeline: false,
    hashline: true,
  },
  all_components: {
    toolGuard: true,
    contextBuilder: true,
    signalPipeline: true,
    hashline: true,
  },
};
```

### 7.2 First Runner Scope

Decision: first implement manifest parsing and metric extraction only.

The first executable milestone should use existing unit/integration tests to
validate component switch behavior. Real agentic trials come later, after runner
isolation and protected metric extraction are verified.

Initial candidate tasks for the manifest:

- `precise-edit`
- `multi-file-patch`
- `search-before-read`
- `preference-aware-edit`
- `failure-recovery-edit-mismatch`

### 7.3 Metric Availability

Decision: every metric in the first runner must be trace-bound or verifier-bound.

If a metric is not currently available from protected trace, Run Archive, or
verifier output, mark it as `blocked_for_trace_grader` in the manifest instead of
estimating it from agent-authored text.

## 8. Recommendation

Approve the RFC with two constraints:

1. The first implementation should build `AblationConfig`, the manifest, and
   metric extraction before real agentic trials.
2. Cases should not be frozen until the runner proves it can produce comparable
   metrics for baseline and at least one component-only config.
